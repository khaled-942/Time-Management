# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm start` — dev server (`ng serve`) at http://localhost:4200
- `npm run build` — production build into `dist/time-management/` (browser + server bundles; only the routes in `prerender-routes.txt` are prerendered)
- `npm run serve:ssr:Time-Management` — run the built SSR Express server (`dist/time-management/server/server.mjs`)
- `npm test` — Karma/Jasmine unit tests
- Single spec: `npx ng test --include src/app/app.component.spec.ts` (add `--watch=false` for one run)
- Database: `npx supabase@2.121.0 db push` applies new files in `supabase/migrations/` (project is linked: ref `lvlgezwylzopnbkzwdhg`); `npx supabase@2.121.0 functions deploy send-push --no-verify-jwt` deploys the push function
- Deploy: `npx vercel@latest deploy --prod` from the `Nabil` branch (`vercel.json`: static output of `dist/time-management/browser`, every extensionless path → `index.csr.html`; Git deploys of `main` are disabled)

No linter is configured. The only existing spec is `src/app/app.component.spec.ts`.

## Architecture

Angular 18 app with standalone components, SSR (Express + `CommonEngine` in `server.ts`, `src/main.server.ts`, `src/app/app.config.server.ts`), and Supabase (Auth + Postgres + Realtime + one Edge Function, via `@supabase/supabase-js`) as the only backend. The Supabase URL, publishable key and VAPID public key live in `src/environments/environment.ts`. Hosting is Vercel (static; `server.ts` is only used by `serve:ssr` locally). UI uses PrimeNG 17 + PrimeFlex, FullCalendar, Chart.js, and jsPDF (payslips, loaded on demand).

- **Routing** (`src/app/app.routes.ts`): every page is lazy-loaded with `loadComponent`. Guards in `src/app/shared/guards/` wait for Supabase Auth to restore the session (`AuthService.currentUser()`): `loggedInFormGuard` also requires the localStorage `user` session to match, `allowedGuard` keeps logged-in users off login/register, `adminGuard` reads `isAdmin` from the `users` table. Access is actually enforced in the database: row-level security policies, guard triggers and security-definer RPCs in `supabase/migrations/` (the port of the old `firestore.rules`). The salary route was removed — salary is rendered inside the dashboard, but `src/app/salary/` (`SalaryService`, `PayslipService`, models) is used by the dashboard.
- **Data access**: all database access goes through services in `src/app/shared/services/` plus `AuthService`, using the one client in `SupabaseService` (`must()`/`maybe()` unwrap responses; `uid` is the signed-in id; `watch(table, load)` re-runs a query on Realtime changes). Columns are quoted camelCase so rows match `src/app/shared/models.ts`; timestamp columns are wrapped in a `Timestamp` (`toDate()`/`toMillis()`, like Firestore's) by `withTimestamps`. Tables: `users` (row created by the `handle_new_user` trigger on sign-up; the first account becomes admin), `user_private` (salary + report settings, owner-only), `days` (key `userId`+`dayId`), `holidays`, `leaveRequests` (`LeaveService`), `notifications` (`NotificationService`, live), `auditLog` and `lockedPeriods` (`PayrollService`), `teams` and `projects` (`OrgService`; membership changes via the `save_membership`/`clear_leader`/`delete_team` RPCs), `tasks`, `work_logs`, `task_activity` (`TaskService`, live), `time_entries` (`TimeEntryService`), `push_subscriptions` (`PushService`). `directory` is a view over `users` (`DirectoryService`), so it never needs syncing. `ProductionReportService` reads your work logs, days and holidays to build the monthly production report. Schema changes go in a new migration file.
- **Saving days**: always use `HttpRequestsService.saveDayEvent` — it refuses days in a locked payroll period for non-admins (`PERIOD_LOCKED`), merges the write, and appends an `auditLog` entry. Approving leave (`LeaveService.approve`) writes paid-leave days through it too.
- **Notifications** always carry both `userId` and `audience` (one of them `''`); the insert policy requires it. Admin-wide ones use `audience: 'admins'` and per-reader `readBy` arrays, updated only through the `mark_notification_read` RPC.
- **Shell**: `AppComponent` renders `SideBarComponent` (sections, mobile drawer below 1024px) and `NavBarComponent` (breadcrumb, notifications bell, theme toggle) when logged in; page titles come from `PAGE_TITLES` in the navbar. Each page uses the global `.page` / `.page-header` / `.card` / `.stat-card` / `.pill` / `.empty-state` classes from `src/styles.scss`.
- **Session state**: login stores `user` (JSON with `id`, `token`, `date`) and `isAdmin` in localStorage; `AuthService.loginStatusChanged` (EventEmitter) notifies layout components. Components read the current user id from `localStorage.getItem('user')` rather than from the Supabase session.
- **Theming**: design tokens (light + dark) and mixins (`card`, `eyebrow`, `mobile`) are in `src/styles/_theme.scss`; PrimeNG is restyled from those tokens in `src/styles/_primeng-overrides.scss`. Dark mode: `ThemeService` sets `<html data-theme>` (saved in localStorage, otherwise follows the OS); `index.html` applies it before first paint. Never hard-code colours — use the tokens, so both themes work. Charts read token values via `getComputedStyle` and rebuild on `ThemeService.mode$`. Fonts: Inter (text) and JetBrains Mono (numbers, labels).
- **PWA**: installable app via `@angular/service-worker` (production builds only; `ngsw-config.json` falls back to `index.csr.html`), `public/manifest.webmanifest` and `public/icons/`. The registered worker is `public/sw.js`, which `importScripts('ngsw-worker.js')` and adds push handling — keep it that way, two workers can't share a scope. The shell pads for `env(safe-area-inset-*)` so it works full-screen on phones.
- **OS push notifications** (standard Web Push): every new `notifications` row fires the `push_notification` trigger, which posts its id (pg_net) to the `send-push` Edge Function (`supabase/functions/send-push`; URL in `private.settings`). The function re-reads the row, claims it once (`pushed`) and sends to the recipients' `push_subscriptions` with `web-push`. Devices opt in from the bell panel or Profile (`PushService`; removed on sign-out). Messages are `{ data: { title, body, link, tag } }` and `sw.js` shows them, so Angular's worker doesn't show them twice. `environment.vapidKey` is the public VAPID key; the private one is the function's `VAPID_PRIVATE_KEY` secret (both must change together). Push is off in dev builds. iPhones only get pushes in the installed (Home Screen) app.
- **Shared helpers**: day status labels/colours in `shared/utils/day-status.ts`, money/time/CSV formatting in `shared/utils/format.ts`.

## Business rules to preserve

- **Work-schedule rules live in `src/app/shared/utils/work-schedule.ts`** — use its helpers instead of re-deriving dates. `new Date("YYYY-MM-DD")` parses as UTC; use `parseLocalDate`.
- **Reporting period is the 11th → 10th (both inclusive)**, not a calendar month, named after the month it ends in (`periodContaining`, `latestPeriodForMonth`). Dashboard, calendar, and salary calculations all assume this window — don't change it casually.
- **Day rows** (`days`, one per `userId` + `dayId` = YYYY-MM-DD): `start` (date string used for range queries/ordering), `in`/`out` (local `YYYY-MM-DDTHH:mm`; `out` is missing while someone is checked in), `isDayOff`, `dayOffType` (0 = paid day off, -1 = absent, 1 = task), `isLate`, `isEarlyLeave`, `lateExcuse`, `earlyLeaveExcuse`.
- **Schedule**: work starts 09:00 and ends 17:00; the short day ends 13:30 (Thursday before 1 April 2025, Saturday from then on). Friday is the only weekend.
- **Salary** (`SalaryService.calculateSalaryForPeriod`): the full monthly salary minus deductions. Each person sets their own salary on the Profile page; it is stored in `user_private.salary` (`HttpRequestsService.getSalary`/`setSalary`), which only the owner can read — admins never see salaries (no salary on the Admin page). Daily rate = salary / 30. Each absence (`dayOffType` -1) deducts one day; paid leave, task days, Fridays and days without records cost nothing. Lateness tiers are cumulative (0–30 min: 1st warning, 2nd ¼, 3rd ½ more, 4th+ one day each; 31–60 min: 1st ½, then one day each; >60 min: one day each). Any late *or* early-leave excuse exempts the day. Missing salary throws `Error('NO_SALARY_DEFINED')`, which the dashboard shows as a "salary missing" state. Excuse hours are capped at 4h per period. `SalaryCalculation.deductionLines` explains each deduction (0-day lines are warnings).
- **Leave**: leave requests are switched off for now (`FEATURES.leaveRequests` in `src/app/shared/features.ts` hides the route, sidebar link and admin tab). 21 paid days per calendar year (`ANNUAL_LEAVE_DAYS`); requested days count working days only (no Fridays/holidays).
- **Roles and teams**: one `role` per person (`'pm' | 'leader' | 'member'`, missing = member) plus a `teamId`, both set by admins (Admin → Users / Teams) and blocked for users by the `guard_users_update` trigger. `isAdmin` is separate. A team has exactly one leader (`teams.leaderId`, who also has `role: 'leader'` and that `teamId`); always change membership through `OrgService.saveMembership`, which keeps the team, the new leader and the demoted previous leader consistent in one transaction (the `save_membership` RPC). PMs have no team.
- **Projects**: one shared list (`projects`), used by the private tracker and team tasks. Admins and PMs create/edit/archive; only admins delete.
- **My Tasks (private tracker)**: `time_entries` (`TimeEntryService`), each `{ title, projectId ('' = none), date, start, end ('' while the timer runs), note }`. Only the owner can read or write it — no admin/PM/leader access, by design. At most one running entry; a timer still running after midnight is stopped at 23:59 of its day. Weeks on the page run Saturday → Friday.
- **Work logs** (`work_logs`, `WorkLog`): time spent on a board task — `{ date, hours, country, kind, pages, note }` plus the task's title/project copied in and who logged it. Assignees and the reviewer (and PMs/admins) log time on unarchived tasks; people delete their own. Everyone who sees the task sees its logs; the report reads your own logs across tasks (`TaskService.myWorkLogs`). A task with logged time can't be deleted (`HAS_WORK_LOGS`, also an `on delete restrict` foreign key) — archive it.
- **Task activity & archive**: `TaskService` writes one `task_activity` row per change (`recordChanges`: status, assignees, fields, checklist ticks, sub-tasks, time logged, archive), best-effort and never edited; the task dialog shows/hides it (remembered in localStorage). `archived` tasks are read-only, hidden from the board unless "Show archived" is on, and only the reviewer/PMs/admins archive or restore (`canArchiveTask`).
- **Production report** (dashboard → Work log, `shared/services/production-report.service.ts`): covers a *calendar month* (1st → last day, not the payroll period) and is due on the 30th (`REPORT_DUE_DAY`, the last day in shorter months). Built from your board work logs (task title = sub-project, project name, country, kind, pages, hours) — not from My Tasks. Exports Word (`docx`, day-by-day table) and Excel (`exceljs`, project × day grid), both imported on demand; their colours are fixed print colours, not theme tokens. Organization, department and dated main assignments (`{ label, start, end }`, a band under each working day in range; the latest start wins on overlap) live in `user_private` (`organization`, `department`, `assignments`; `organization` null = never saved).
- **Projects page**: each project opens a list of its board tasks (those the viewer can see) with creator, assignees, status and due date. The `production-report-reminder` pg_cron job (`private.production_report_reminder()`, Africa/Cairo time) sends every active person a notification on the due day.
- **Directory**: `users` rows are private (owner/admin only), so names, avatars, roles and teams that others need (task assignees, pickers) come from the `directory` view, which exposes only those columns.
- **Team tasks & Board** (`/board`, `tasks`): columns `backlog → todo → in_progress → review → changes → done`, ordered by a numeric `order` (gaps of 1024, a dropped card takes the midpoint). The creator is the reviewer. Permissions live in `shared/utils/task-access.ts` and are mirrored in the database (`can_see_task`, the tasks policies and the `guard_tasks_update` trigger) — change both together: PMs/admins see and manage everything; leaders create tasks only for their own team (`teamIds == [their team]`); members can't create; assignees may only change `status` (not to `changes`/`done`), `order` and `checklist` on unfinished tasks. `teamIds` (assignees' teams) decides who can see a task; `TaskService.watch` reads all tasks and row-level security filters them. Moving to `changes` requires a `reviewNote`; moving to `done` clears it.
- **Sub-tasks & task side effects**: a sub-task has `parentId`; the parent keeps `subtasks: { [id]: done }` so everyone sees progress even when sub-tasks belong to other teams. Always write tasks through `TaskService.create/update/move/remove` (pass the task as it was *before* the change): it updates the parent's map atomically (the `sync_parent` RPC, security definer so a sub-task's assignee can update a parent they aren't on), moves the parent to `review` once every sub-task is done (and tells its reviewer), and sends bell notifications (assigned, needs review, changes requested, approved, reopened — never to yourself). Notifications link to `/board?task=<id>`, which opens that task. Parents with sub-tasks can't be deleted.
- **Accounts**: admins set `isAdmin` and `active` on the Admin page; `active: false` signs the person out and blocks writes. Email confirmation is off (`supabase/config.toml`, pushed with `supabase config push`).

## SSR gotchas

Only `/login` and `/register` are server-rendered (prerendered via `prerender-routes.txt`); `server.ts` sends every other path the client-only `index.csr.html`, because those pages depend on the browser-stored session. Add new public pages to both lists. `ng serve` still server-renders every route, so a login flash in dev is expected.

Code runs on the server during SSR/prerender, so never touch `localStorage`, `window`, or `document` unguarded (especially in constructors/`ngOnInit`). The codebase uses either `isPlatformBrowser(this.platformId)` or `typeof window !== 'undefined' && typeof window.localStorage !== 'undefined'` — follow the same pattern.
